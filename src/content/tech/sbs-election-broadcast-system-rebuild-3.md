처음엔 델파이가 싫어서 시작했다. 솔직히 그게 8할이었다. 그런데 막상 문제를 하나씩 적어보니, 델파이는 문제의 일부였다. 델파이를 React로 바꾸기만 하면 우리는 "20년 뒤 후배들이 욕할 React 프로젝트"를 하나 더 만드는 셈이었다.

(20년 뒤에도 React가 있을지는 모르겠지만)

## 해결하려던 문제
리빌드를 시작하기 전에 팀에서 문제를 네 가지로 정리했다.

### 첫번째, 비용 ### 
선거마다 외주 개발자 2명이 2개월씩 붙어야 했다. 지난 편에서 말한 "지난 소스 복사하고 기도하기"를, 우리는 매 선거마다 돈을 내고 반복하고 있었던 셈이다.

델파이를 다룰 수 있는 사람은 점점 줄어들고, 그 몇 안 되는 사람을 선거철마다 모셔와야 했다. 선거는 예정대로 오지만, 델파이 개발자는 예정대로 오지 않는다.

### 두번째, 구조

화면, 로직, 그리고 방송 그래픽 장비(바이폰)와의 TCP 통신이 델파이 프로그램 하나에 강하게 결합되어 있었다.

지난 편에서 보여준 `TFormA001`을 다시 떠올려보자. 그 폼 하나 안에서 버튼을 그리고, 서버에서 데이터를 받고, 데이터를 가공하고, 바이폰으로 소켓을 쏜다. 화면 하나를 고치려고 열었는데 통신 코드가 같이 딸려 나오는 구조다.

### 세번째, 배포


델파이 프로그램은 exe를 컴파일해서 부조정실 방송 PC에 배포하는 방식이었다.

평소에는 큰 문제가 아니다. 문제는 방송 중에 오류가 났을 때다.

코드 수정 → exe 빌드 → 부조정실에 급하게 연락 → 파일 전달 → "이걸로 다시 받아서 실행해주세요"

생방송 중인 부조정실에 전화를 걸어서, 지금 쓰고 있는 프로그램을 끄고 새 파일로 다시 받아달라고 부탁하는 것이다. (그 전화를 거는 사람의 심정을 상상해보시라)

1편에서 "프로그램이 갑자기 에러가 나면 다른 바이폰을 방송하거나, 아나운서가 시간을 끌 수도 있다"고 썼는데, 그 '시간'의 정체가 바로 이 과정이다. (아나운서님들께 이 자리를 빌려 감사의 말씀을…)

### 네번째, 사용성

아래는 기존에 쓰던 실시간 모니터링 상황판 화면이다.


![](./images/델파이-상황판-1.png)

선거 당일 PD님과 작가님들이 가장 궁금한 건 결국 이런 것들이다.

* 지금 어디가 접전이지?
* 아직 개표 안 된 지역은 어디지?
* 다음에 어떤 그래픽을 준비해야 하지?

그런데 기존 화면은 일단 **눈에 안 들어온다**.

회색 바탕에 깨알 같은 글씨, 모든 숫자가 똑같은 크기와 굵기로 나열되어 있다. 중요한 숫자와 덜 중요한 숫자의 구분이 없고, 그나마 있는 강조는 빨간 글씨 몇 개가 전부다. 전국 개표율 99.9%와 시도별 미개표 수 0이 화면에서 똑같은 무게로 보인다.

정보가 없는 게 아니다. 필요한 숫자는 다 있다. 문제는 그걸 순간적으로 눈으로 확인할 수 없다는 것이다.

예를 들어 '접전 득표율차 3.0 이하'라는 조건을 걸어두면 접전 지역이 '몇 개'인지는 알려준다. 그런데 그게 '어디'인지는 표를 위아래로 훑으면서 숫자를 하나하나 읽어야 알 수 있다.

생방송 중에, 시시각각 숫자가 바뀌는 표에서. PD님 콜 한 번에 다음 그래픽이 결정되는 그 몇 초 안에.

(이 화면을 보면서 방송 흐름을 짜셨던 분들께 존경을 표한다)

선거방송에서 상황판은 '데이터를 보여주는 화면'이 아니라 '판단을 돕는 화면'이어야 했다. 숫자를 읽게 만드는 게 아니라, 한눈에 보이게 만들어야 했다.

## Before / After


그래서 바꾼 구조는 이렇다.


![](./images/선거방송_아키텍처_wide-1.png)


선관위 → 사내 DB까지의 흐름은 그대로다. 바뀐 건 그 뒤다.

Before에서는 **델파이 ↔ 바이폰**이 직접 연결되어 있었다. After에서는 이걸 **(프론트 + 백엔드) ↔ 바이폰**으로 바꿨다.

이 결정은 프론트와 백엔드가 같이 내렸다. 핵심은 두 가지다.

### 1. TCP는 서버가 한다

새 프론트엔드는 TCP를 모른다.

바이폰 장비와 소켓으로 통신하는 일은 전부 Spring 서버가 맡고, 프론트엔드는 "이 메뉴를, 이 데이터로, 이 장비에 보내주세요"라는 요청만 HTTP로 보낸다.

```ts
export async function postData(body: any) {
  const apiUrl = import.meta.env.VITE_FORWARD_SERVER_URL;

  try {
    const response = await fetch(apiUrl, {
      method: "POST",
      headers: { "Content-Type": "application/json" },
      body: JSON.stringify(body), // { pairIp, menuId, data }
      signal: AbortSignal.timeout(FETCH_TIMEOUT),
    });

    return await response.json();
  } catch (error) {
    throw new Error("스프링 서버로 데이터 전송 실패. 에러 코드 : " + error);
  }
}
```

이게 프론트에서 바이폰으로 데이터를 보내는 코드의 거의 전부다.

* `pairIp`: 어느 바이폰 장비로 보낼지
* `menuId`: 어떤 그래픽(메뉴)인지
* `data`: 그 그래픽에 들어갈 데이터

송출(ONAIR) 버튼을 누르면 이 세 가지를 JSON으로 묶어서 Spring 서버에 던지고, 서버가 검증한 뒤 바이폰 프로토콜에 맞춰 TCP로 쏴준다.

별거 아닌 것 같지만, 이 결정이 이후 모든 것의 출발점이었다. **소켓을 화면에서 떼어내니까, 화면이 브라우저로 갈 수 있었다.**

브라우저는 TCP 소켓을 직접 열 수 없다. 델파이 시절처럼 화면이 장비와 직접 통신해야 했다면, 우리는 웹을 선택지에 올리지도 못했을 것이다.


### 2. 화면을 두 종류로 나눈다

새 프론트엔드는 성격이 전혀 다른 두 화면으로 나뉜다.

**실시간 대시보드: 10초마다 자동 갱신**

PD님, 작가님들이 보는 화면이다. 앞에서 본 기존 상황판을 대체한다.

전국 개표 현황, 1위 후보, 시도별 개표율, 시군구 접전 상황, 첫 개표 지역 등을 표 대신 카드와 지도로 보여준다. 정당은 색으로, 접전 지역은 따로 모아서, 미개표 지역은 지도 위에서 바로 보이게 했다. "어디가 접전이지?"라는 질문에 숫자를 읽지 않고 보고 답할 수 있게 하는 게 목표였다.

그리고 이 화면은 무조건 최신이어야 한다. 그래서 10초마다 알아서 데이터를 새로 받아온다.

**송출 메뉴: 조회 버튼을 눌렀을 때만 갱신**


바이폰을 운영하시는 PD님이 쓰는 화면이다. 1편에서 설명한 바로 그 화면이다. 메뉴를 검색하고, 데이터를 확인하고, 송출 버튼을 누른다.

송출 메뉴는 원래부터 수동이다. PD님이 송출 버튼을 눌러야 바이폰으로 데이터가 전달되고, 바이폰은 ready 상태에서 데이터를 받는 순간 그 데이터로 그래픽을 실행한다.

즉, **버튼을 누르는 순간이 곧 데이터가 확정되는 순간**이다.

웹으로 옮기면서 자동 갱신을 붙이는 건 어렵지 않았다. 대시보드에 이미 붙어 있으니까. 하지만 송출 메뉴에는 일부러 붙이지 않았다.

PD님이 화면에서 눈으로 확인한 숫자와 바이폰으로 넘어가는 숫자는 반드시 같아야 한다. 확인하는 사이에 화면이 혼자 바뀐다면, 그건 **사람이 확인하지 않은 숫자가 방송에 나갈 수 있다**는 뜻이다. 1편에서 '당선' 두 글자는 항상 사람 눈으로 크로스체크한다고 했던 것과 같은 원칙이다.

그래서 송출 메뉴는 조회 버튼을 눌렀을 때만 데이터를 가져온다. 기존 시스템의 이 원칙은 그대로 지켰다.

같은 데이터를 보여주는 화면인데, 하나는 "항상 최신"이 미덕이고 다른 하나는 "확인한 그대로"가 미덕이다.

## 왜 웹이었나 ## 


소켓을 떼어내고 나니, 화면을 무엇으로 만들지는 오히려 쉬운 문제가 됐다.

해결하려던 문제 중 '배포'를 다시 보자. 방송 중 오류가 났을 때 exe를 다시 깔아야 하는 문제를 해결하는 가장 확실한 방법은, **설치 자체를 없애는 것**이었다.

웹이면

* 부조정실 어느 PC에서든 브라우저만 열면 된다
* 서버에 배포하면 모든 운영자가 같은 버전을 쓴다
* 방송 중에 고쳐도 새로고침이면 끝난다

(마지막 줄이 얼마나 중요했는지는 나중에 따로 이야기하겠다)

스택은 React + TypeScript + Vite + Tailwind로 정했다. 거창한 기술 선정 회의 같은 건 없었다. 이유는 현실적이었다.

**프론트엔드 개발자가 1명(나)이고, 2~3달 안에 끝내야 했다.**


가장 익숙하고, 가장 빨리 만들 수 있고, 문제가 생겼을 때 검색하면 답이 나오는 스택. 20년 전 델파이를 고른 분들도 아마 비슷한 이유였을 거라고 생각한다. (그분들은 검색할 곳도 없었겠지만)

다만 TypeScript만큼은 선택이 아니라 필수라고 생각했다.

이 프로젝트는 숫자 하나, 필드 하나가 틀리면 그대로 생방송에 나간다. "런타임에 확인하면 되지"의 런타임이 곧 방송이다. 그렇다면 타입은 무조건 강제하는 게 옳았다.

그게 왜 그렇게 중요했는지는, 바로 다음 이야기에서 보인다.

## 순서에서 키로

지난 편에서 티맥스가 데이터를 보내는 방식을 보여줬다.

```c
fbput(_snd, GIHO_ID, (char *)_szR, 0);
fbput(_snd, DANG_CD, (char *)data[_rk].dangcode, 0);
fbput(_snd, HUBO_NM, (char *)data[_rk].huboname, 0);
fbput(_snd, CNT,     (char *)&data[_rk].cnt, 0);
fbput(_snd, RATE,    (char *)&data[_rk].rate, 0);
```
**FDL은 순서가 곧 의미다.** 받는 쪽(델파이)도 순서대로 꺼내야 하고, 인덱스를 하나만 틀려도 옆 후보의 데이터가 꺼내진다. 그리고 그 실수는 컴파일러도, 테스트도 잡아주지 않는다. 방송 화면이 잡아준다. (최악의 QA)

새 시스템에서는 바이폰 프로토콜을 레코드 단위의 TypeScript 타입으로 전부 다시 정의했다.

```ts
export type REC_Gongtong = {
  MENUID: string;
  KIND: "0" | "1" | "2" | "3" | "4" | "5";
  OPT1: string;
  OPT2: string;
  TIME: string;
  LASTSCENE: "Y" | "N";
};

export type REC_Hubo = {
  GIHO: string;       // 기호
  HUBONAME: string;   // 후보명
  DANGCODE: string;   // 정당코드
  POLLRANK: string;   // 출구조사 순위
  POLLRATE: string;   // 출구조사 득표율
  POLLDEGREE: string; // 출구조사 등급
  DUKPRANK: string;   // 득표 순위
  DUKPCNT: string;    // 득표수
  DUKPRATE: string;   // 득표율
  DEGREE: string;     // 유력/확실/당선 등급
};
```
공통 레코드, 후보 레코드, 선거구 레코드, 투표율 레코드, 의석수 레코드… 이렇게 바이폰이 받는 레코드가 15종류다. 이제 데이터는 순서가 아니라 키로 전달된다. `DUKPRATE` 자리에 `DUKPCNT`를 넣으면 에디터가 빨간 줄을 그어준다.

그리고 레코드를 만드는 곳을 `formatToProtocolRecord()` 한 함수로 모았다.


```ts
case ProtocolRecordType.REC_Sungugu:
  const recSungugu: REC_Sungugu = {
    SIDO: data.SIDO,
    SIDONAME: data.SIDONAME,
    GUGUN: data.GUGUN,
    GUNAME: data.GUNAME,
    OPENRATE:
      data.GAEPYOMAGAM === "완료"
        ? "완료"          // 개표 마감
        : data.OPENRATE === ""
        ? "미개"          // 미개표
        : data.OPENRATE,
    PYOCHA: data.PYOCHA,
    YULCHA: data.YULCHA,
    SGOPT1: data.SGOPT1,
    SGOPT2: data.SGOPT2,
  };
  return recSungugu;
```
`OPENRATE` 부분을 보자. 1편에서 개표 초반에는 "'미개표' 필드가 제대로 전달되는지 중점적으로 확인한다"고 썼다. 델파이 시절에는 이 규칙이 메뉴마다 흩어져 있었고, 사람이 매번 확인해야 했다.

이제 "개표율이 비어 있으면 '미개', 마감됐으면 '완료'"라는 규칙은 이 한 곳에만 있다. 어떤 메뉴에서 보내든, 선거구 레코드는 이 함수를 거친다.

**인덱스 하나 틀리면 옆 후보 데이터가 나가던 시절과는 이렇게 작별했다.**

---

정리하면, 이번 리빌드에서 바꾼 건 언어가 아니라 경계였다.

* 화면과 통신 사이의 경계 → TCP는 서버로
* 실시간 화면과 송출 화면 사이의 경계 → 자동 갱신 vs 수동 조회
* 데이터와 프로토콜 사이의 경계 → 순서 대신 타입

델파이가 문제였던 게 아니라, 모든 게 한 덩어리였던 게 문제였다.

구조는 이렇게 바뀌었다. 그런데 막상 메뉴를 옮기기 시작하자 다른 문제가 기다리고 있었다.

**옮겨야 할 바이폰 메뉴가 184개였다.**
