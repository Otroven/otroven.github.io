선거방송 리빌드 글을 네 편 쓰면서, 마음 한구석에 계속 걸리는 게 있었다.

"TCP는 서버로 뺐다", "순서 대신 타입으로 바꿨다", "지역과 후보는 테마라는 데이터로 뺐다"

다 맞는 결정이었다고 생각한다. 실제로 방송도 잘 나갔다. 그런데 누가 **"왜 그게 맞는데요?"** 라고 물으면, 솔직히 "해보니까 그게 나았어요" 말고는 할 말이 별로 없었다.

그래서 『소프트웨어 아키텍처 101』(마크 리처즈, 닐 포드)을 집어 들었다. 아직 9장까지밖에 못 읽었지만, 읽는 내내 형광펜을 긋다가 멈추고 우리 코드를 떠올리는 일이 반복됐다.

이 글은 책 요약이 아니다. 책에 나온 도구들로 **내가 만든 시스템을 다시 채점해본 기록**이다.

(채점 결과는… 생각보다 나쁘지 않았고, 생각보다 운이 좋았다)

## 모듈성은 공짜로 유지되지 않는다

3장은 모듈성 이야기로 시작한다. 그리고 첫 페이지부터 물리학을 꺼낸다.

소프트웨어 시스템은 **엔트로피가 증가하는 방향으로 움직이는 복잡계**이고, 질서를 유지하려면 계속 에너지를 넣어야 한다는 것이다.

이 문장을 읽자마자 델파이 시절이 떠올랐다.

`20XX_총선 → 20XX_지선 → 20XX_대선`

2편에서 "소스코드도 선거처럼 순환되었다"고 썼다. 그 20년 동안 우리는 에너지를 안 쓴 게 아니다. 오히려 매 선거마다 외주 개발자 2명이 2개월씩 엄청난 에너지를 쏟았다. 문제는 그 에너지가 **질서를 만드는 데가 아니라, 무질서를 한 번 더 복사하는 데** 쓰였다는 점이다.

책에서는 모듈성을 **암묵적 아키텍처 특성**이라고 부른다. 아무도 "모듈 경계를 잘 지켜주세요"라고 요구사항에 적지 않지만, 그게 없으면 코드베이스는 결국 무너진다.

그리고 9장에서 그 결말에 이름을 붙여준다. **진흙잡탕(Big Ball of Mud)**.

책은 진흙잡탕이 생기는 이유를 **코드 품질과 구조에 대한 거버넌스의 부재**로 짚는다. 누구도 의도하지 않았는데, 그렇게 된다는 것이다.

이 부분은 빨간색으로 칠했다. 아무도 진흙잡탕을 만들려고 하지 않는다. 그냥 거버넌스가 없으면 그렇게 된다.

## 응집: "이 클래스, 하는 일이 몇 개야?"

책은 모듈성을 측정하는 세 가지 도구로 **응집(cohesion), 커플링(coupling), 커네이선스(connascence)** 를 소개한다.

응집은 "모듈 안의 파트들이 서로 얼마나 관련되어 있는가"다. 좋은 것부터 나쁜 것 순으로 7단계가 있다.

| 응집 유형 | 한 줄 요약 |
|---|---|
| 기능적 (functional) | 기능에 필요한 것만, 전부 들어 있다 |
| 순차적 (sequential) | A의 출력이 B의 입력 |
| 소통적 (communicational) | 같은 정보를 두고 체인을 이룬다 |
| 절차적 (procedural) | 정해진 순서대로 실행되어야 한다 |
| 일시적 (temporal) | 같은 "시점"에 실행된다는 이유로 묶였다 (ex. 초기화) |
| 논리적 (logical) | 논리적으로만 비슷하다 (ex. `StringUtils`) |
| 동시적 (coincidental) | 같은 파일에 있다는 것 말고는 아무 관계 없음 |

마지막 동시적 응집이 **가장 나쁜 형태**다.

2편의 `TFormA001`을 다시 떠올려보자. 폼 하나 안에서 버튼을 그리고, 서버에서 데이터를 받고, 가공하고, 바이폰으로 소켓을 쏜다. 동시적 응집까지는 아니겠지만, 적어도 기능적 응집이라고 부르기는 어렵다. "UI", "데이터 조회", "프로토콜 변환", "TCP 송신"이라는 네 개의 관심사가 **'같은 메뉴'라는 이유 하나로** 한 클래스에 살고 있었다.

### LCOM: 응집을 숫자로

응집은 주관적이라 측정하기 어렵지만, 그래도 구조적으로 재보려는 시도가 있다. 카이댐버와 케메러의 **LCOM(Lack of Cohesion in Methods)**, 이름 그대로 "메서드 응집 결여도"다.

처음 버전은 이렇다.

```
LCOM = |P| - |Q|   (|P| > |Q| 일 때)
       0           (그 외)

P: 공유 필드에 접근하지 않는 메서드 쌍의 수
Q: 공유 필드를 공유하는 메서드 쌍의 수
```

말로 풀면 **"공유 필드를 통해 공유되지 않는 메서드의 수"** 다. 점수가 높을수록 나쁘다.

책의 그림이 직관적이었는데, 필드 A·B·C와 메서드 m1·m2·m3가 있는 클래스 세 개를 비교한다.

* **클래스 X**: 메서드들이 필드를 서로 엇갈려 공유한다 → LCOM 낮음, 응집 좋음
* **클래스 Y**: A-m1, B-m2, C-m3가 각자 따로 논다 → LCOM 높음. 사실상 클래스 3개가 한 집에 사는 것
* **클래스 Z**: 일부는 엮여 있고 C-m3만 따로 논다 → C-m3는 떼어내도 된다

`TFormA001`은 아마 Y와 Z 사이 어딘가였을 것이다. TCP 송신 메서드는 UI 컴포넌트 필드(`txtA01`~`txtA16`)를 전혀 건드리지 않는다. 3편에서 **"TCP는 서버가 한다"** 고 떼어낸 결정은, LCOM 관점에서 보면 클래스 Z의 C-m3를 밖으로 꺼낸 것과 같다.

(그때는 이런 이름을 몰랐다. 그냥 "브라우저에선 소켓이 안 열리니까"였다)

### 그래서 정답은? "경우에 따라 다릅니다"

책에는 이런 예시가 나온다. '고객 관리' 모듈에 고객 추가/수정/조회/알림, 그리고 **고객 주문 조회/취소**가 들어 있다. 마지막 두 개는 '주문 관리'로 빼야 할까?

책의 답은 "경우에 따라 다르다"이고, 대신 이런 질문을 던지라고 한다.

* 주문 관리에 작업이 정말 2개뿐인가? 그렇다면 그냥 두는 게 낫다
* 고객 관리 모듈은 앞으로 계속 커질 예정인가?
* 주문 관리가 동작하려면 고객 정보를 많이 알아야 하는가?

그리고 **이런 질문 자체가 아키텍트 업무의 핵심인 트레이드오프 분석**이라고 말한다.

4편의 테마 이야기가 정확히 이거였다. '컬러프레임 2인', '커튼월 2인', '긁어라 대선 복권'은 TV에서 보면 전혀 다른 메뉴다. 그런데 데이터 관점에서 질문을 던지면 답이 달라진다. "이 메뉴들이 하는 일이 정말 다른가?" 아니었다. 그래서 20개 메뉴가 같은 `page.tsx`를 쓰게 됐다.

## 커플링을 숫자로: 불안정도와 메인 시퀀스

응집이 모듈 "안"의 이야기라면, 커플링은 모듈 "사이"의 이야기다.

* **구심 커플링(Ca, afferent)**: 나를 호출하는, **들어오는** 연결의 수
* **원심 커플링(Ce, efferent)**: 내가 호출하는, **나가는** 연결의 수

(이름이 너무 비슷해서 헷갈리는데, 책에서 알려준 니모닉이 좋았다. 알파벳에서 a가 e보다 먼저니까 '들어오는' 게 먼저, e는 exit의 e라서 '나가는' 쪽)

이걸로 몇 가지 지표를 만들 수 있다.

```
추상도   A = Σ추상 요소 / Σ구상 요소         (0 ~ 1)
불안정도 I = Ce / (Ce + Ca)                 (0 ~ 1)
메인 시퀀스로부터의 거리 D = |A + I - 1|      (0 ~ 1)
```

**불안정도(I)** 가 높다는 건, 내가 의존하는 게 많다는 뜻이다. 여러 클래스를 호출해서 일을 위임하는 클래스는, 그중 하나만 바뀌어도 같이 깨질 가능성이 크다.

**D**는 추상도와 불안정도의 균형을 본다. A + I = 1인 대각선(메인 시퀀스)에 가까울수록 건강하다.

* 오른쪽 위로 치우치면 **쓸모없는 구역(zone of uselessness)**: 추상화만 잔뜩 해서 아무도 못 쓰는 코드
* 왼쪽 아래로 치우치면 **고통스러운 구역(zone of pain)**: 추상화 없이 구현만 꽉 찬, 그런데 모두가 의존하는 코드

### `formatToProtocolRecord()`는 어디쯤일까

이 지표를 읽자마자 3편에서 자랑했던 그 함수가 떠올랐다.

> 레코드를 만드는 곳을 `formatToProtocolRecord()` 한 함수로 모았다.

간단하게 계산해보자. (숫자는 설명을 위한 가정이다)

```ts
// 가정: 이 함수를 호출하는 메뉴 페이지가 100개, 이 함수가 의존하는 건 레코드 타입 정의 1개
const Ca = 100; // 들어오는 연결
const Ce = 1;   // 나가는 연결

const I = Ce / (Ce + Ca); // ≈ 0.0099  → 매우 안정적
const A = 0;              // 거대한 switch-case, 인터페이스나 추상화 없음 → 완전 구상

const D = Math.abs(A + I - 1); // ≈ 0.99 → 메인 시퀀스에서 거의 최대로 멀다
```

결과는 **D ≈ 1, 고통스러운 구역 한가운데**다.

처음엔 좀 당황했다. "한 곳에 모았다"는 게 장점이라고 썼는데, 지표는 위험하다고 말하고 있었다.

그런데 곰곰이 생각해보면 둘 다 맞다.

* "개표율이 비어 있으면 '미개', 마감됐으면 '완료'" 같은 규칙이 **한 곳에만 있는 것**은 분명한 장점이다
* 동시에 이 함수를 잘못 고치면 **바이폰 메뉴 전체가 같이 깨진다**는 것도 사실이다

그래서 책은 메트릭에 한계가 있다고 분명히 말한다. 구조는 알려주지만, 그게 **왜** 그렇게 생겼는지는 알려주지 않는다. 소프트웨어 아키텍처 제2법칙, **"어떻게"보다 "왜"가 더 중요하다**.

우리가 할 수 있는 건 이 함수가 고통스러운 구역에 있다는 걸 **알고 쓰는 것**이다. 레코드 타입별로 케이스를 분리하고, 이 함수만큼은 테스트를 가장 촘촘하게 붙여두는 것. (다음 선거 전 TODO에 적어뒀다)

## 커네이선스: 같이 바뀌어야 하는 것들

이번 3장에서 가장 많이 밑줄을 그은 개념이 **커네이선스(connascence)** 다.

밀러 페이지-존스의 정의를 내 말로 풀면 이렇다.

> 한쪽을 바꿨을 때 다른 쪽도 같이 바꿔야 시스템이 정상이라면, 그 둘은 커네이선스를 갖고 있다.

우리말로 하면 '변화 종속성' 정도다. 이게 기존 커플링보다 좋았던 점은, **어떤 방식으로** 엮여 있는지를 구분해서 이름을 붙여준다는 것이다.

### 정적 커네이선스 (소스 코드 레벨)

* **명칭(CoN)**: 이름이 일치해야 한다. 가장 흔하고 가장 바람직하다
* **타입(CoT)**: 타입이 일치해야 한다
* **의미(CoM)**: 값의 의미가 일치해야 한다 (ex. `int TRUE = 1`)
* **알고리즘(CoA)**: 알고리즘이 일치해야 한다 (ex. 서버/클라이언트 해시)
* **위치(CoP)**: **값의 순서가 일치해야 한다**

### 동적 커네이선스 (런타임 레벨)

* **실행(CoE)**: 실행 순서가 중요하다
* **타이밍(CoT)**: 실행 시점이 중요하다 (ex. 경합 조건)
* **값(CoV)**: 여러 값이 함께 바뀌어야 한다 (ex. 분산 트랜잭션)
* **아이덴티티(CoI)**: 같은 엔티티를 참조한다

그리고 책의 [그림 3-5]가 정말 좋았다. 아이덴티티부터 명칭까지 아래에서 위로 화살표가 하나 그려져 있고, 그 위에 **"이 방향으로 리팩터링"** 이라고 적혀 있다. 아래쪽(동적)일수록 강하고 위험하고, 위쪽(정적, 특히 명칭)일수록 약하고 안전하다.

### FDL은 위치 커네이선스였다

위치 커네이선스(CoP)의 예시를 읽다가 웃음이 나왔다.

```java
void updateSeat(String name, String seatLocation)

updateSeat("14D", "Ford, N");  // 타입은 맞는데, 의미는 완전히 틀렸다
```

이건 2편, 3편에서 내가 계속 이야기했던 **티맥스 FDL** 그 자체다.

```c
fbput(_snd, GIHO_ID, (char *)_szR, 0);
fbput(_snd, DANG_CD, (char *)data[_rk].dangcode, 0);
fbput(_snd, HUBO_NM, (char *)data[_rk].huboname, 0);
fbput(_snd, CNT,     (char *)&data[_rk].cnt, 0);
fbput(_snd, RATE,    (char *)&data[_rk].rate, 0);
```

보내는 쪽(티맥스)과 받는 쪽(델파이)이 **순서**로 엮여 있다. 둘 다 `char *`라서 타입 검사는 통과하고, 인덱스 하나만 밀려도 옆 후보의 데이터가 나간다. 3편에서 "최악의 QA는 방송 화면"이라고 썼는데, 이제 그 이유를 한 단어로 설명할 수 있다. **위치 커네이선스는 컴파일러가 잡아주지 않는다.**

그리고 3편의 해결책은 정확히 책이 말하는 화살표 방향이었다.

```ts
export type REC_Hubo = {
  GIHO: string;
  HUBONAME: string;
  DANGCODE: string;
  DUKPCNT: string;    // 득표수
  DUKPRATE: string;   // 득표율
  // ...
};
```

순서(CoP)로 엮여 있던 것을 **이름(CoN)과 타입(CoT)** 으로 엮이게 바꿨다. `DUKPRATE` 자리에 `DUKPCNT`를 넣으면 에디터가 빨간 줄을 긋는다. 커네이선스가 사라진 건 아니다. 여전히 프론트와 서버는 같은 필드명을 알아야 한다. 다만 **더 약하고, 도구가 검사해줄 수 있는 형태**로 바뀌었다.

`formatToProtocolRecord()` 안의 '미개'/'완료' 규칙은 **의미 커네이선스(CoM)** 를 한 곳에 가둔 것이다. 델파이 시절에는 "빈 문자열이면 미개표"라는 의미를 메뉴마다 따로 알고 있어야 했다.

### 정도의 규칙, 지역성의 규칙

짐 웨이리치가 남긴 두 가지 규칙도 적어둔다.

* **정도의 규칙(Rule of Degree)**: 강한 커네이선스를 약한 커네이선스로 바꿔라
* **지역성의 규칙(Rule of Locality)**: 요소 간 거리가 멀수록 약한 커네이선스를 써라

두 번째가 특히 와닿았다. FDL의 위치 커네이선스가 그렇게 위험했던 건, 그게 **C 서버와 델파이 클라이언트라는, 서로 다른 프로세스·다른 언어·다른 팀** 사이에 걸쳐 있었기 때문이다. 같은 함수 안에서 매개변수 순서가 맞아야 하는 것과는 차원이 다르다.

그리고 4편 마지막에 예고했던 문제.

> 송출 버튼을 아주 빠르게 두 번 누르면 어떻게 될까?

이건 이제 정확히 뭐라고 불러야 하는지 안다. **타이밍 커네이선스**다. 화살표의 가장 아래쪽, 가장 강하고 가장 다루기 어려운 종류다. (1편에서 throttling을 걸었다고 가볍게 썼는데, 그게 왜 '가볍게' 쓸 일이 아니었는지는 다음 편에서…)

## 모듈에서 컴포넌트로: 최상위 분할

8장은 모듈을 **물리적으로 패키징한 것**을 컴포넌트라고 부르면서 시작한다. 자바의 jar, 닷넷의 dll, 그리고 델파이 시절 우리의 메뉴별 DLL도 컴포넌트다.

그리고 아키텍트가 가장 먼저 내려야 할 결정 중 하나로 **최상위 분할(top-level partitioning)** 을 꼽는다.

```
[기술 분할]                    [도메인 분할]
- Presentation                 - CatalogCheckout
- Controller                   - ShipToCustomer
- Service                      - UpdateInventory
- Persistence                  - Reporting
```

* **기술 분할**: 프레젠테이션/서비스/퍼시스턴스처럼 기술적 능력으로 나눈다. 퍼시스턴스 코드가 한 레이어에 모여 있어서 찾기 쉽다. 대신 `CatalogCheckout` 같은 비즈니스 흐름 하나가 **모든 레이어에 흩어진다**
* **도메인 분할**: 워크플로나 도메인으로 나눈다. 자주 일어나는 변경의 유형이 구조에 더 잘 드러난다. 대신 DB 접근, API 컨트롤러, 데이터 변환 같은 **기술적 구현 코드가 도메인마다 파편화된다** (이건 내가 책 여백에 적어둔 메모다)

어느 쪽이 더 낫다고 단정할 수 없다. 아키텍처 제1법칙, **모든 것은 트레이드오프**.

### 그럼 선거방송 프론트는?

4편의 구조를 다시 보면, 우리는 둘을 섞었다.

```
src/
├── pages/menus/          ← 도메인 분할: 메뉴 하나 = 폴더 하나
│   ├── 301/page.tsx
│   ├── 302/page.tsx
│   └── ...
└── components/           ← 기술 분할: 공통 부품
    ├── MenuHeader*       (기본 / 재쿼리 / 타이머 / PT)
    └── *MenuTable        (후보 중심 / 지역 중심 / 장면별 그리드)
```

최상위는 메뉴(도메인)로 나누고, 메뉴들이 공통으로 쓰는 헤더와 테이블은 기술적으로 뽑아냈다. 델파이 시절 "메뉴 하나 = DLL 하나"가 순수한 도메인 분할이었다면, 지금은 도메인 분할 위에 **기술 분할한 공통 레이어를 얹은** 형태다.

책이 말한 도메인 분할의 단점(기술 코드 파편화)을 공통 컴포넌트로 막고, 기술 분할의 단점(전역 커플링)은 메뉴 폴더 독립성으로 막은 셈이다. 물론 그 대가로 공통 헤더를 고치면 184개 메뉴가 같이 영향을 받는다. (공짜는 없다)

### 엔티티 함정

8장에서 빨간색을 칠한 부분이 하나 더 있다. **엔티티 함정(entity trap)**.

책의 경매 시스템 예시에서, 어떤 아키텍트가 `경매 관리자`, `품목 관리자`, `입찰 관리자` 컴포넌트를 만든다. DB에 경매 테이블이 있으니 경매 관리자, 품목 테이블이 있으니 품목 관리자. **DB 엔티티 하나당 컴포넌트 하나를 기계적으로 찍어낸 것**이다.

책은 이게 아키텍처가 아니라고 단호하게 말한다. 그냥 DB를 컴포넌트에 관계형으로 매핑한 것, 그러니까 **DB 구조를 코드 형태로 받아 적은 것**에 불과하다고.

이 부분을 읽고 4편의 메뉴 이야기를 다시 봤다. 만약 우리가 DB 테이블 기준으로 컴포넌트를 나눴다면 `후보 테이블 컴포넌트`, `선거구 테이블 컴포넌트`, `투표율 테이블 컴포넌트`가 생겼을 것이다. 그런데 실제로 PD님이 하는 일은 그게 아니다.

> 정해진 지역 N곳에서, 정해진 후보들의 개표 결과를 가져와서, 수동으로 한 장씩 넘긴다.

이건 테이블이 아니라 **워크플로**다. 그리고 이 워크플로 단위로 묶었기 때문에 20개 메뉴가 같은 파일을 공유할 수 있었다. (이것도 그때는 몰랐다. 메뉴를 하나씩 옮기다 "어? 이거 다 똑같네?" 한 게 전부였다)

### 같은 기능, 다른 아키텍처 특성

8장 GGG 사례에서 가장 인상 깊었던 장면이다.

`BidCapture`는 입찰자와 경매인의 입찰을 모두 받는다. 기능적으로는 합리적이다. 어디서 온 입찰이든 똑같이 처리하면 되니까. 그런데 **아키텍처 특성**을 보면 이야기가 달라진다.

* 입찰자는 수천 명 단위로 늘어날 수 있다 → **확장성, 탄력성**이 중요
* 경매인은 한 명이다. 그 대신 경매인의 접속이 끊기면 재앙이다 → **신뢰성, 가용성**이 중요

그래서 `BidCapture`와 `AuctioneerCapture`로 쪼갠다. **기능이 같아도 요구되는 특성이 다르면 다른 컴포넌트다.**

이걸 읽으면서 3편의 화면 분리가 떠올랐다.

| | 실시간 대시보드 | 송출 메뉴 |
|---|---|---|
| 사용자 | PD님, 작가님들 | 바이폰 운영 PD님 |
| 갱신 | 10초마다 자동 | 조회 버튼 눌렀을 때만 |
| 핵심 특성 | **최신성** | **확인한 그대로 (정합성)** |

같은 개표 데이터를 보여주는 화면이다. 그런데 하나는 "항상 최신"이 미덕이고, 다른 하나는 "사람이 확인한 숫자와 방송에 나가는 숫자가 같아야 한다"가 미덕이다. 그래서 나눴다.

3편을 쓸 때는 이걸 "원칙"이라고만 불렀는데, 책은 이걸 **아키텍처 특성에 따른 컴포넌트 재구성**이라고 부른다.

## 분산 컴퓨팅의 오류 8가지

9장에서는 아키텍처 스타일을 크게 두 가지로 나눈다. 전체 코드를 한 단위로 배포하는 **모놀리식**, 원격 프로토콜로 여러 단위를 배포하는 **분산형**.

그리고 분산형을 고르는 순간 반드시 마주치는 문제로, 1994년 피터 도이치와 동료들이 정리한 **분산 컴퓨팅의 오류(fallacies)** 8가지를 소개한다.

1. 네트워크는 믿을 수 있다
2. 레이턴시는 0이다
3. 대역폭은 무한하다
4. 네트워크는 안전하다
5. 토폴로지는 절대 안 바뀐다
6. 관리자는 한 사람뿐이다
7. 운송비는 0이다
8. 네트워크는 균일하다

전부 "그렇다고 믿고 싶지만 사실은 틀린 것"들이다.

### 우리는 홉을 하나 늘렸다

3편에서 아키텍처를 이렇게 바꿨다.

```
Before:  델파이 ─────── TCP ───────▶ 바이폰
After:   브라우저 ── HTTP ──▶ Spring ── TCP ──▶ 바이폰
```

소켓을 화면에서 떼어내서 웹으로 갈 수 있었다. 그런데 이 결정은 **네트워크 홉을 하나 더 늘린 것**이기도 하다. 9장을 읽고 나니 이 화살표 하나가 다르게 보였다.

**오류 #1, 네트워크는 믿을 수 있다.** 3편의 `postData()`를 다시 보면 이 한 줄이 있다.

```ts
signal: AbortSignal.timeout(FETCH_TIMEOUT),
```

책에서 말하는 바로 그 **타임아웃**이다. Spring 서버가 멀쩡해도 네트워크 때문에 응답이 안 올 수 있고, 생방송 중에 송출 버튼이 무한정 매달려 있으면 안 된다. 책은 여기서 한발 더 나아가 **서킷 브레이커**까지 이야기한다. 우리 시스템에는 아직 없다.

**오류 #2, 레이턴시는 0이다.** 책에서 형광펜을 가장 굵게 칠한 문장이다.

> 아키텍트는 평균 레이턴시를 반드시 알아야 한다.

그리고 평균보다 더 중요한 게 **95~99번째 백분위수**, 이른바 **'긴 꼬리(long tail)'** 다. 평균이 60ms여도 p95가 400ms일 수 있다.

1편에서 송출 타이밍 이야기를 했다.

> 너무 빨리 누르면 → 아나운서 멘트와 싱크가 맞지 않고, 먼저 그래픽이 보인다.
> 너무 늦게 누르면 → 멘트는 나갔는데, 화면에는 아직 이전 그래픽이…

PD님 콜에 맞춰 버튼을 눌렀는데 p99에 걸려서 0.5초 늦게 그래픽이 뜬다면? 일반 웹 서비스에서는 아무도 모를 지연이, 선거방송에서는 방송 사고다. 솔직히 고백하면, 지금 우리 시스템의 **송출 요청 p95가 몇 ms인지 나는 모른다.** (이번 글에서 가장 뼈아픈 깨달음이다)

**오류 #3, 대역폭은 무한하다.** 여기서 **스탬프 커플링(stamp coupling)** 이라는 개념이 나온다.

책의 예시는 이렇다. 위시리스트 서비스가 고객 이름(200byte) 하나가 필요해서 고객 프로필 서비스를 호출하는데, 프로필 서비스는 45개 속성, 500KB를 통째로 돌려준다. 초당 2,000번 호출되면 **1GB**다.

해결 방법으로 프라이빗 엔드포인트, 필드 셀렉터, GraphQL, 컨슈머 주도 계약 등을 소개하지만, 결론은 하나다. **서비스 간에는 최소한의 데이터만 주고받아라.**

우리 송출 요청 바디를 다시 보면 꽤 괜찮게 설계했다는 생각이 든다.

```ts
{ pairIp, menuId, data }  // 어느 장비로, 어떤 메뉴를, 어떤 데이터로
```

필요한 것만 담았다. 다만 대시보드의 10초 폴링은 다시 볼 필요가 있다. 화면에 보이는 카드 몇 장을 위해 매번 전체 개표 데이터를 받아오고 있지는 않은지. 수십 명이 동시에 대시보드를 띄워놓는 선거 당일 밤이라면 더더욱.

**오류 #7, 운송비는 0이다.** 레이턴시와 헷갈리기 쉬운데, 여기서 운송비는 시간이 아니라 **'단순한 REST 호출'에 드는 진짜 비용**이다. 서버, 게이트웨이, 방화벽, 서브넷… 분산할수록 인프라가 늘어난다. 사내 서버 한 대에 Spring과 React를 같이 띄우고, 그 위에 Gitea runner까지 올려둔 우리 팀 입장에서는 꽤 현실적인 이야기다.

### 아키텍처 퀀텀: 모놀리스냐, 분산이냐

8장 마지막에 이 질문이 나온다. 컴포넌트를 다 식별했으면 이제 결정해야 한다. **모놀리스로 갈 것인가, 분산으로 갈 것인가.**

책의 기준은 **아키텍처 퀀텀**의 수다. 시스템 전체가 하나의 아키텍처 특성 세트로 충분하면 모놀리스가 유리하고, 컴포넌트마다 특성이 크게 다르면 분산이 필요하다.

GGG에서는 `VideoStreamer`/`BidStreamer`(수만 명에게 실시간 전송, **극도의 읽기 성능과 확장성**)와 입찰/결제(**데이터 정합성과 신뢰성**)가 한 프로세스에 섞여 있으면, 읽기 트래픽이 폭주할 때 결제까지 같이 느려진다. 그래서 떼어낸다.

(이건 책 여백에 길게 적어둔 메모를 거의 그대로 옮겼다)

우리 선거방송 시스템도 마찬가지다. 대시보드는 읽기 전용에 동시 접속이 많고, 송출은 요청 수는 적지만 단 한 건도 틀리면 안 된다. 지금은 같은 Spring 서버가 둘 다 받고 있다. 선거 당일 밤 대시보드 폴링이 몰릴 때 송출 요청이 영향을 받지 않는다고, 나는 지금 확신할 수 있을까?

…없다. 다음 선거 전에 반드시 확인해봐야 할 질문이 하나 생겼다.

## 정리

책을 읽고 내 시스템을 다시 채점해보니 이랬다.

* **응집**: `TFormA001`에서 TCP를 떼어낸 건 LCOM 관점에서 따로 놀던 메서드-필드 쌍을 분리한 것이었다
* **커플링**: `formatToProtocolRecord()`는 **고통스러운 구역**에 있다. 장점이자 리스크다
* **커네이선스**: FDL → TypeScript 타입 전환은 **위치 커네이선스를 명칭/타입 커네이선스로** 끌어올린 것이었다. 그리고 다음 숙제인 송출 연타는 **타이밍 커네이선스**다
* **컴포넌트**: 메뉴는 도메인(워크플로)으로, 공통 부품은 기술로 나눈 하이브리드다. 엔티티 함정은 운 좋게 피했다
